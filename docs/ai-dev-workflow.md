# AI 开发流程：编号与结果状态语义

本仓的 PR 描述里有一张「需求与验收映射」表（见 [`.github/pull_request_template.md`](../.github/pull_request_template.md)）。
这份文档只规定**编号规则**与**结果状态语义**。需求与验收条件可以直接写在 PR 描述里，不要求来自外部工单。

## 编号规则

| 前缀 | 含义 | 例子 |
| --- | --- | --- |
| `REQ-*` | 需求条目：要达成什么 | `REQ-COM-02`、`REQ-WIN-01` |
| `AC-*` | 验收条件：怎么判定需求达成了 | `AC-COM-02`、`AC-WIN-01` |
| `F-*` | 审计发现项（findings） | `F-01`、`F-22` |
| `N-*` | 未验证 / 环境限制项 | `N-09`、`N-12` |
| `P-*` | 已验证的正向结论 | `P-06` |

- 一个 `REQ` 可以对应多个 `AC`；每条 `AC` 在映射表里单列一行。
- 有外部工单/审计来源时，编号必须与其原文一致，不要自行重编号或合并；没有外部来源时，直接在 PR 描述中写清需求与验收条件并自拟编号即可。
- 没有需求来源的维护性改动，编号列写 `无 / None`，但「测试」章节仍须给出实际执行结果。

## 结果状态语义

结果列**只能**填下列五个值之一：

| 状态 | 含义 | 不成立的写法 |
| --- | --- | --- |
| `PASS` | 有实际执行证据，且证据覆盖该条要求 | 「测试已写」「CI 全绿」 |
| `FAIL` | 有实际执行证据，且证明要求未达成 | — |
| `BLOCKED` | 因外部依赖/权限/环境无法继续，**且已说明缺什么** | 用「后续优化」代替 |
| `NOT-VERIFIED` | 证据不足，既不能判定通过也不能判定失败 | 把未知直接写成 `PASS` |
| `APPROVED-EXCEPTION` | 用户明确批准不满足该条要求，**必须附批准记录** | 开发者自行豁免 |

### 证据分级

同一条 `AC` 的证据强度不同，映射表里要写清楚是哪一级：

1. 源码结构 / 字符串检查 —— 只能证明形状；
2. 组件测试 + mock —— 只能证明局部状态；
3. 真实宿主 + fake 外部服务 —— 证明装配、路由、鉴权；
4. 真实数据库 / 真实设备 / 隔离外部账号 —— 证明持久化与平台行为。

mock 不能替代需要真实证据的链路；平台限制（例如 Linux 上无法执行 Windows 运行时行为）保持 `NOT-VERIFIED`，不得用静态检查冒充通过。
